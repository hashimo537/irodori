# 9-1 要件定義と設計

📝 **前提知識**: このセクションは README の内容を前提としています。

Part 4 では、ここまで学んだ技術を1つのアプリに統合します。家族スケジュール共有アプリをゼロから Laravel 10 + Sail で構築し、1対多リレーション・グローバルスコープによる認可・外部API連携・くりかえしデータの展開を通して実装します。

## 導入: 要件には「書かれていないこと」がある

模擬案件では、要件を読み解いて自分で設計に落とす力が問われます。要件には、はっきり書かれていることと、行間に隠れていることがあります。

「習い事を管理したい」という一文からは、**それが毎週くりかえすのか、1回きりなのか**が読み取れません。ここを設計者が決めないと、テーブルもリレーションも定まりません。

このセクションでは、短い要件から ER図・テーブル・画面を設計します。コードはまだ書きません。

---

## 🧠 先輩エンジニアの思考プロセス

要件を読んでいて一番神経を使うのは、**「くりかえすか、1回きりか」「誰のものか」「消したらどうなるか」** の3点です。

とくに「くりかえし」は要注意で、まじめに実装するとカレンダーの繰り返しルール（iCal の RRULE。「毎月第2火曜」のような指定ができる仕組み）が必要になり、それだけで数日かかります。ここは最初に**どこまで対応するかの線を引いて**おかないと、あとから無限に膨らみます。

もうひとつが「誰のものか」。今回は家族でデータを共有するので、**よその家族のデータが見えない仕組み**を最初に決めておく必要があります。これを後回しにすると、全画面に条件を書き足す羽目になります。

## 要件を読み解く

今回作るアプリの要件は、次のとおりです。

> ユーザーは、登録・ログインして、家族の予定を管理できる。家族には複数の子どもを登録でき、子どもごとに色を設定する。子どもには毎週くりかえす習い事（曜日・時間・場所）を登録でき、それとは別に単発の予定（運動会・歯医者など）も登録できる。予定には終日のものもある。家族は招待コードを共有することで、同じ予定を見られるようにする。提出物の期限、記念日（誕生日など）も管理できる。月表示では天気予報を表示する。

この文には、設計者が決めるべき「行間」がいくつもあります。

### ① 習い事はくりかえすのか、1回きりか

「毎週くりかえす習い事」とあります。ここで線を引きます。

**判断: くりかえしは「毎週おなじ曜日」だけに限定する。**

「毎月第2火曜」「隔週」は捨てます。子どもの習い事の9割は毎週なので、これで実用上困りません。そして、この判断が設計を大きく変えます。

**判断: 習い事はDBに1行だけ持ち、画面に出すときに各週へ展開する。**

「毎週火曜 16:30-18:00」を1行持つだけなら、`day_of_week`（曜日）・`start_time`・`end_time` の3列で表せます。展開処理をコントローラに書けば、何週先でも表示できます。**展開したデータをDBに保存しません。** これが今回いちばん大きな設計判断です。

### ② 習い事と単発の予定は、同じテーブルか

習い事は「曜日」を持ち、単発の予定は「日付」を持ちます。性質が違います。

**判断: `lessons`（習い事）と `events`（単発の予定）を別テーブルにする。**

無理に1つにまとめると「日付と曜日のどちらかが必ず null」という気持ちの悪いテーブルになります。性質が違うものは分けます。

### ③ 予定は誰のものか

「家族の予定」とあります。持ち主は子どもですが、「家族でおでかけ」のように特定の子どものものではない予定もあります。

**判断: `events.member_id` は null 可。null を「家族ぜんいん」の意味に使う。**

### ④ 子どもはログインするのか

子どもはログインしません。`users` に混ぜるとメールアドレスとパスワードが必須になって不自然です。

**判断: 「ログインする人」＝ `users`、「予定の登場人物」＝ `members` として分ける。**

これは重要な発想です。**認証の対象とデータの登場人物は別物**として扱います。

### ⑤ 家族の共有はどうやるか

「招待コードを共有する」とあります。1人が複数の家族に所属することは要件にありません。

**判断: `users.family_id` を1本持たせる（1人1家族）。中間テーブルは作らない。**

多対多にすると `family_user` という中間テーブルが要りますが、今回は割り切ります。離婚・再婚家庭などは考え出すとキリがないので、**割り切った理由をコメントに残す**ことをセットにします。

### ⑥ よその家族のデータが見えないようにするには

要件に明示はありませんが、これが破れたらアプリとして終わりです。

**判断: グローバルスコープで、全クエリに自動で `where family_id = ?` を付ける。**

毎回コントローラで条件を書く方式は、1か所でも書き忘れたら穴が開きます。人間は必ず書き忘れるので、**仕組みで縛ります**（9-3で実装）。

### ⑦ 終日の予定はどう表すか

**判断: `start_time` が null なら終日、とする。**

`is_all_day` という真偽値の列を足す手もありますが、「終日なのに時刻が入っている」という矛盾したデータが作れてしまいます。**矛盾したデータを作れない設計のほうが強い**です。

### ⑧ 記念日（誕生日）はどう持つか

毎年くりかえします。習い事と同じ発想が使えます。

**判断: 日付ではなく「月」と「日」だけを持つ。**

年をまたぐたびにレコードを作る必要がなくなります。生まれた年を任意で持たせれば、年齢も計算できます。

### ⑨ 削除したらどうなるか

| 親を消したとき | 子はどうなる | 設定 |
|---|---|---|
| 家族を消した | 子ども・予定・習い事も消す | `cascadeOnDelete()` |
| 家族を消した | ユーザーは残す（family_id を null に） | `nullOnDelete()` |
| 子どもを消した | その子の習い事も消す | `cascadeOnDelete()` |
| 子どもを消した | 予定は残す（家族ぜんいんの予定になる） | `nullOnDelete()` |
| お迎え担当のユーザーが抜けた | 予定は残す | `nullOnDelete()` |

「道連れにしていいか」を1つずつ判断します。ここを決めずにマイグレーションを書くと、あとで整合性が壊れます。

## ER図

読み解いた関係をER図にまとめます。`families` を中心に、すべてのテーブルが `family_id` でぶら下がる形です。

```
                        families
                        ├── id                 PK
                        ├── name               「はしもと家」
                        ├── invite_code        UK  ← これ1つで家族を共有する
                        ├── location_name          天気予報の地点
                        ├── latitude
                        └── longitude
                             │
      ┌──────────┬───────────┼───────────┬────────────┬──────────────┐
      │          │           │           │            │              │
    users     members     lessons      events       tasks      anniversaries
  family_id   family_id   family_id   family_id   family_id     family_id
   (null可)       │           │           │            │              │
      │           └───────────┴───────────┴────────────┴──────────────┘
      │                    member_id でつながる
      │            （events / tasks / anniversaries は null 可）
      │
      └──── pickup_user_id ────→ events / lessons（お迎え担当）
```

### 関係の読み方

- `users` は `families` に属する（`belongsTo`）。ただし登録直後はまだ家族がないので **null 可**
- `members`（子ども）は `families` に属し、`lessons` を複数持つ
- `events` は `members` に属するが、**null なら家族ぜんいん**
- `lessons` と `events` は `users` を「お迎え担当」として参照する（`pickup_user_id`）
- `anniversaries` は毎年くりかえすので、日付ではなく月・日を持つ

## テーブル定義

ER図を、列・型・制約のレベルまで具体化します。これが 9-3 でマイグレーションを書くときの設計図になります。

### families

家族。招待コードを持つのがポイントです。

| 列 | 型 | 制約・備考 |
|---|---|---|
| id | bigint | 主キー |
| name | string | 「はしもと家」 |
| invite_code | string(8) | **一意**。家族を共有するための合言葉 |
| location_name | string | 天気予報の地点名。null 可 |
| latitude | decimal(8,5) | 緯度。null 可 |
| longitude | decimal(8,5) | 経度。null 可 |
| created_at / updated_at | timestamp | |

### users

Laravel 標準のユーザーテーブルに、1列だけ足します。

| 列 | 型 | 制約・備考 |
|---|---|---|
| family_id | bigint | 外部キー（families.id）。**null 可**（登録直後はまだ家族がない）。ON DELETE SET NULL |

### members（子ども）

| 列 | 型 | 制約・備考 |
|---|---|---|
| id | bigint | 主キー |
| family_id | bigint | 外部キー。ON DELETE CASCADE |
| name | string | 「ゆい」 |
| color | string(7) | `#8FB2C9` のような色コード |
| sort_order | tinyint | 表示順 |

### lessons（習い事＝毎週くりかえし）

| 列 | 型 | 制約・備考 |
|---|---|---|
| id | bigint | 主キー |
| family_id | bigint | 外部キー。ON DELETE CASCADE |
| member_id | bigint | 外部キー（必須）。ON DELETE CASCADE |
| pickup_user_id | bigint | 外部キー（users）。お迎え担当。null 可。ON DELETE SET NULL |
| title | string | 「スイミング」 |
| place | string | 「市民プール」。null 可 |
| day_of_week | tinyint | **0=日 … 6=土** |
| start_time | time | 16:30 |
| end_time | time | 18:00 |
| starts_on | date | 通いはじめた日 |
| ends_on | date | やめた日。通っている間は null |

🔑 `starts_on` / `ends_on` があることで、「4月にやめた習い事が3月のカレンダーにはちゃんと出る」が実現できます。これがないと、やめた瞬間に過去の記録まで消えてしまいます。**くりかえすデータには期間を持たせる**のが定石です。

### events（単発の予定）

| 列 | 型 | 制約・備考 |
|---|---|---|
| id | bigint | 主キー |
| family_id | bigint | 外部キー。ON DELETE CASCADE |
| member_id | bigint | 外部キー。**null 可 = 家族ぜんいん**。ON DELETE SET NULL |
| pickup_user_id | bigint | 外部キー（users）。null 可。ON DELETE SET NULL |
| title | string | |
| place | string | null 可 |
| date | date | |
| start_time | time | **null なら終日** |
| end_time | time | null 可 |
| note | text | メモ。null 可 |
| created_by | bigint | 外部キー（users）。誰が入れたか |

インデックスとして `['family_id', 'date']` を張ります。週表示のたびに「この家族の、この期間の予定」を検索するためです。

### tasks（提出物）

| 列 | 型 | 制約・備考 |
|---|---|---|
| id | bigint | 主キー |
| family_id | bigint | 外部キー。ON DELETE CASCADE |
| member_id | bigint | 外部キー。null 可 |
| title | string | 「給食袋」 |
| due_date | date | 期限。null 可 |
| is_done | boolean | 既定値 false |

### anniversaries（記念日）

| 列 | 型 | 制約・備考 |
|---|---|---|
| id | bigint | 主キー |
| family_id | bigint | 外部キー。ON DELETE CASCADE |
| member_id | bigint | 外部キー。null 可（結婚記念日など） |
| title | string | 「ゆいの誕生日」 |
| month | tinyint | 1〜12 |
| day | tinyint | 1〜31 |
| start_year | smallint | 生まれた年。null 可（入れると年齢が出る） |

📝 **日付型を使わない理由**: 毎年くりかえすので「2018-04-12」という1日を指す型では表せません。月と日だけを持てば、何年先でも同じ判定ができます。習い事で「曜日だけ」を持ったのと同じ発想です。

## 画面の設計

すべてログイン必須とし、未ログインの場合はログイン画面に誘導します。さらに「家族に入っていること」も条件にします。

| 機能 | 画面 | 備考 |
|---|---|---|
| 認証 | 登録・ログイン・ログアウト | Fortify |
| 家族 | 家族をつくる／招待コードで参加 | **家族に入る前だけ通れる道** |
| 家族 | 招待コードを見せる | |
| 家族 | 地域の設定（天気予報） | |
| 子ども | 一覧＋登録・編集・削除 | 色の選択つき |
| 習い事 | 一覧・登録・編集・削除 | 曜日と時間 |
| 予定 | 登録・編集・削除 | 一覧は週表示が兼ねる |
| 提出物 | 一覧＋登録・チェック・削除 | |
| 記念日 | 一覧＋登録・編集・削除 | |
| **週タイムライン** | ホーム画面 | このアプリの心臓 |
| 月カレンダー | 見わたす画面 | 天気つき |

🔑 **ルートの入れ子**がポイントです。

```
auth（ログイン必須）
 ├── 家族をつくる／参加する        ← 家族がなくても通れる
 └── has.family（家族に入っている人だけ）
      ├── 週タイムライン
      ├── 月カレンダー
      └── 子ども・習い事・予定・提出物・記念日
```

家族作成の画面を内側に入れてしまうと、**家族がないと弾かれる画面に、家族を作るために行かされる**という無限リダイレクトになります。ここは設計時点で気づいておきたいところです。

## バリデーションの方針

入力の検証はコントローラの `validate()` で行います。主な方針を決めておきます。

- **予定**: `title` は必須・40文字以内。`date` は必須・日付形式。`start_time` は「終日でなければ必須」（`required_without:all_day`）。`end_time` は `after:start_time`。`member_id` は任意だが、指定されたら存在確認（`exists:members,id`）
- **習い事**: `member_id` は必須。`day_of_week` は `between:0,6`。`start_time`・`end_time` は `date_format:H:i` で、終了は `after:start_time`。`ends_on` は `after:starts_on`
- **子ども**: `name` は必須。`color` は**用意した6色のいずれか**（`Rule::in()`）。自由入力にすると変な色が入る
- **記念日**: `month` は `between:1,12`、`day` は `between:1,31`
- **お迎え担当**: **同じ家族のユーザーのIDだけ**を許す（`Rule::in()` で家族のユーザーIDの配列を渡す）
- **招待コード**: `size:8`

🔑 `exists:members,id` だけでは不十分な場面があります。`<select>` の値は改ざんできるので、よその家族の子どものIDを送られる可能性があります。今回はグローバルスコープが二重に守ってくれますが、**バリデーションと認可の両方を書く**のが正しい姿勢です。

## 📝 メモ: このアプリに多対多はない

3-1 で学んだ多対多（ピボットテーブル）は、今回は使いません。すべて1対多で表せるからです。

「使える技術だから使う」ではなく、**必要な形を選ぶ**のが設計です。無理にピボットを入れると、かえって読みにくくなります。

将来「1つの予定に複数の子どもが参加する」という要件が出てきたら、そこで初めて `event_member` というピボットが必要になります。

## ✅ 設計の確認

このセクションは設計が成果物です。次を自分の言葉で説明・決定できれば、設計が固まっています。

- 要件のあいまいな点（くりかえしの範囲・予定の所有者・子どもとユーザーの違い・削除の連鎖）を、設計上の判断として説明できる
- 6つのテーブルからなるER図を説明できる
- 習い事を「曜日だけ」で持ち、表示時に展開する理由を説明できる
- 終日を `start_time` の null で表す理由を説明できる
- カスケード削除を効かせる箇所と、null にする箇所を区別できる
- グローバルスコープで家族を守る方針を説明できる
- ルートの入れ子（`auth` の内側に `has.family`）が必要な理由を説明できる

## ✨ まとめ

- 要件には「行間」がある。**くりかえしの範囲・所有者・削除の連鎖**を読み解いて、設計上の判断に落とす
- 本アプリは `families`・`users`・`members`・`lessons`・`events`・`tasks`・`anniversaries` の7テーブルで構成する
- くりかえすデータ（習い事・記念日）は**展開して保存せず、表示時に組み立てる**
- 矛盾したデータを作れない形にする（終日は `start_time` の null で表す）
- 家族の分離は、毎回条件を書くのではなく**グローバルスコープで仕組みとして縛る**

次の 9-2 では、Sail でプロジェクトを作り、共通レイアウトとCSSを配置します。
